# CYRVIS：眼动辅助 GUI Agent 加速调研

日期：2026-11-18。范围：当前 Cyrvis 分支代码、已有本机日志及公开论文；未修改运行策略，未做新的性能基准实验。

## 结论

眼动可作为目标位置的先验：减少输入画面、缩小定位候选范围、减少澄清与错误操作，进而降低部分任务的总耗时。但注视不是动作授权，也不保证与当前任务目标一致。使用普通云模型 API，无法通过提示词直接修改模型内部 attention 或剪枝视觉 token。

当前最适合本项目的路线：先补分阶段计时，随后比较“无眼动全屏”“全屏加眼动提示”“低清全局图加高清眼动区域”，最后测试眼动目标与可复用动作模板结合。应分别报告单次模型调用提效和端到端任务提效。

## 当前项目实际做了什么

- GUI 模型：本机配置为 doubao-seed-2.1-lite；操作器为 Local Computer Operator。
- 看屏问答：desktop-inspector.ts 获取主屏截图，按最新有效眼动坐标裁剪，再通过 inspector.ts 调用视觉模型。截图仅在提问时发送，不是每一帧上传。
- GUI 操作：gui-adapter.ts 在任务启动时追加眼动坐标提示；主 GUIAgent 循环仍按常规截图—模型—执行流程运行。尚未实现每步眼动裁剪、区域坐标映射及加速策略。
- 语音、看屏问答与 GUI 操作是不同耗时链路，不能拿看屏问答的速度证明完整 GUI 任务提速。

## 已查到的本机慢点

日志来源：工作区 cyrvis-gaze-demo-latest.log。只提取耗时，不复制截图、会话内容、密钥或配置全文。

| 观察 | 证据 | 能得出的结论 |
| --- | --- | --- |
| 6 次成功 GUI 模型请求 | 9872、24848、17838、11402、4228、22988 ms；中位数 14620 ms | 该小样本里，请求耗时是显著开销，不能视为稳定服务 SLA |
| 另有 2 次模型计时约 30 秒 | 30006、30004 ms | 与代码中的 30 秒请求超时吻合；需要单独统计失败与重试 |
| 每轮额外等待 | 本机 loopIntervalInMs=1500；GUIAgent.ts 在轮末 sleep | 10 轮若均走该等待分支，累计约 15 秒；这与模型本身无关 |
| 模型失败还会等待再试 | runAgent.ts 配置 maxRetries=5，GUIAgent.ts 的 minTimeout=30000 ms | 最多首次加 5 次重试，且有退避等待；请求失败会放大尾延迟 |
| SDK 内层重试 | Model.ts 的 OpenAI 客户端 maxRetries=0 | 此处没有再叠加 OpenAI SDK 默认重试，不应误诊为双重重试 |
| 本地操作也存在等待 | nut-js 的普通点击前 sleep(100)，wait 动作为 sleep(5000) | “执行慢”应拆成真实输入、页面加载、固定等待、模型重复决策 |

模型返回到下一轮等待开始的 6 个日志间隔约为 12–598 ms，但其中混合了解析、界面回调和动作执行，不能把它当作纯鼠标耗时。

上述请求时长包含服务端处理和网络等开销。没有服务端 tracing，无法继续严格拆成排队、图片编码、prefill、decode 和传输，更不能断言全是豆包算力慢。

相关代码：

- apps/ui-tars/src/main/services/runAgent.ts：模型配置、重试与 loopIntervalInMs。
- packages/ui-tars/sdk/src/GUIAgent.ts：截图、调用、执行、重试退避和轮间等待。
- packages/ui-tars/sdk/src/Model.ts：图片预处理、模型调用与 30 秒超时；当前已设置 thinking disabled。
- packages/ui-tars/operators/nut-js/src/index.ts：本机输入和显式 wait。

## 外部研究能支持什么

### 人眼注视可以指导视觉输入压缩

[Eye Gaze Tells You Where to Compute: Gaze-Driven Efficient VLMs](https://arxiv.org/html/2509.16476v1) 使用真实人眼注视形成 ROI，并可附加低分辨率全局图；无需重新训练基础模型。论文在 VOILA-COCO 视觉问答、Qwen2.5-VL-3B/7B 和 A100 环境上评估 token、FLOPs 与回答质量，报告特定配置下视觉 token 最多减少 93.1%，FLOPs 约减少 50%。

这些不是 CYRVIS、豆包云 API、普通摄像头或 GUI 点击任务上的实测结果，也不是端到端时延减少 93.1%。过小裁剪可能丢失布局与关系信息；不同模型对裁剪大小的反应也不同。

### GUI 慢通常需要同时看模型调用与步骤数

[OSWorld-Human（v2）](https://arxiv.org/html/2506.16042v2) 对 Agent S2/GTA1 的时延分析显示，规划、判断和反思调用占据主要时间，截图和输入动作占比较小，并提出减少调用开销、减少步骤、改善定位与回退。其统计来自特定框架和任务，不可直接作为本项目的阶段占比。

### 减少重复决策比只加快一次识别更值得测试

[ActionEngine（v2）](https://arxiv.org/abs/2602.20502v2) 通过可复用应用状态与程序化执行减少逐步规划调用，界面变化时再回退修复。其 WebArena 结果不代表 macOS 原生应用，但支持我们测试“已知动作路径复用、失败再回退”的工程方向。这类提效不依赖眼动，必须设置无眼动对照。

## 可落地方案与边界

| 优先级 | 方案 | 眼动的具体作用 | 验证与风险 |
| --- | --- | --- | --- |
| P0 | 分阶段计时与失败统计 | 无；先建立基线 | 定位模型请求、截图预处理、输入、页面等待和重试的占比 |
| P1 | 低清全局图＋高清注视 ROI | 将细节预算集中到用户目标附近 | 总图像输入必须实际变小；两张图并不天然更省。比较 token 与墙钟时间 |
| P1 | 注视区域内匹配 OCR/可访问性控件 | 将不稳定点坐标变成少量控件候选 | 不保证所有应用支持；不遍历和上传整棵控件树作为默认策略 |
| P1 | 位置不确定时扩大区域或退回全屏 | 使用估计误差决定 ROI 大小 | 不能为了省 token 把目标裁掉；失效时沿用普通 GUI 流程 |
| P2 | 已知应用动作模板 | 眼动帮助选择目标，模板减少后续模型轮次 | 每个关键界面变化后验证；弹窗、登录和版本变化时回退 |
| P2 | 短时结果缓存与界面变化检测 | 同一注视区域未变化时复用读屏结果 | 结合应用/窗口、图片变化和时效校验，不能只按坐标缓存 |
| P3 | 开源模型内部视觉 token 筛选 | 注视可指导 token 预算 | 需要控制模型推理栈，当前豆包托管 API 路线不能直接实现 |

交互规则：

1. 用户说“这里/这个”时，冻结指令时刻附近的稳定注视作为引用对象。
2. 用户明确指定应用、对象或位置时，以明确指令为准，眼动只辅助消歧。
3. 任务执行期间用户可以看别处；不可每一步强行跟随视线改变执行目标。
4. 注视不是点击、发送或购买的指令。仅有注视时继续本地追踪，不自动执行动作。
5. 云端预取会改变当前“提问才传图”的行为，不能默认为用户开启。可以先只做本地候选准备。

裁剪后若用于点击，必须保存截图尺寸、ROI 原点和缩放系数，将局部坐标映射回正确显示器的桌面逻辑坐标，执行前确认截图仍对应当前页面。看屏问答只需描述区域，GUI 操作则必须完成这个坐标闭环。

## 验证实验

先做同一个模型、同一账户、同样输出预算下的探索性对比：

| 条件 | 输入与策略 | 回答的问题 |
| --- | --- | --- |
| A | 无眼动，全屏 GUI 基线 | 当前原始速度与成功率 |
| B | 全屏＋眼动坐标提示 | 单靠提示能否减少澄清或错误步骤 |
| C | 低清全局＋高清眼动区域，失败退回全屏 | 真正减少视觉输入后是否提速，失败代价多少 |
| D | C＋候选控件或动作模板 | 减少规划调用是否进一步降低任务总时长 |

建议选 10 个可复位任务，各条件至少重复 3 次，交错执行以降低服务负载与缓存影响。初期以只读与可逆操作为主，例如解释注视报错、读取指定段落、切换指定标签、操作测试页面按钮；避免用真实发消息作为性能测试。

保持初始界面、目标、指令、窗口和分辨率一致。另设人工准确坐标条件和真实摄像头眼动条件，区分“算法可能收益”与“眼动误差损失”。显式目标任务与“这个/这里”任务分别统计，避免通过让基线缺少必要信息来制造优势。

记录：

- 指令结束到首个正确动作、到任务验证完成的 P50/P90；失败任务的耗时与成功率同时报告。
- 截图/编码、模型请求、解析、输入动作、页面等待、重试分别计时。
- API 输入/输出 usage；不能简单把文件体积或像素比例当 token 比例。若服务未返回视觉 token，明确只能比较总输入 token。
- 调用次数、操作步骤、错误点击、澄清次数、ROI 回退率、超时率。
- 眼动 FPS、CPU/GPU 使用与本地候选处理耗时；单列启动/校准时间，不能完全忽略眼动自身成本。

目前只有已有日志的初步诊断，没有 A/B 结果。可论证的产品方向是“用用户注意力缩小目标搜索范围、减少任务决策”，尚不能宣称本项目已经实现固定倍数加速。单纯眼动裁剪已有公开研究，创新点应在不精确眼动下的可靠 GUI 操作、任务级调用缩减及可重复验证上建立。
